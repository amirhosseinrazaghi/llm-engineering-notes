# توکن‌سازی و معیارهای عملکرد در مدل‌های زبانی بزرگ

## 🧩 چرا این مبحث جدا از [[chat bot theory]] است؟

اونجا فقط تعریف کلی «توکن» رو دیدی. اینجا می‌ریم تو جزئیات: دقیقاً متن چطور قدم‌به‌قدم به توکن و عدد تبدیل می‌شه، و چطور سرعت و هزینه‌ی این فرآیند رو اندازه می‌گیریم.

---

## ۱. مسیر کامل یک پیام (Text → Tokenizer → Token → Token ID)

### تشبیه ساده

> مثل فرستادن یه پیام با کد مورس. اول جمله رو به علائم (نقطه و خط) می‌شکنی (توکن‌سازی)، بعد هر علامت یه معنی عددی مشخص داره که طرف مقابل می‌فهمه (شناسه توکن). کامپیوتر هم دقیقاً همینه — فقط عدد می‌فهمه، نه حروف.

### مراحل قدم‌به‌قدم

۱. **متن خام (Text):** همون چیزی که کاربر تایپ می‌کنه، مثل `"سلام چطوری؟"`. ۲. **توکنایزر (Tokenizer):** یک الگوریتم (معمولاً از خانواده BPE) که متن رو بر اساس یه واژه‌نامه‌ی از پیش آموزش‌دیده، به تکه‌های کوچیک‌تر می‌شکنه. ۳. **توکن (Token):** خروجی مرحله قبل — می‌تونه یه کلمه کامل، بخشی از کلمه، یا یه علامت نگارشی باشه (تعریف کامل‌ترش تو [[chat bot theory]]). ۴. **شناسه توکن (Token ID):** هر توکن تو واژه‌نامه‌ی مدل یه عدد ثابت داره؛ مدل عملاً به‌جای دیدن حروف، فقط این عددها رو می‌بینه. بعد از این مرحله، این عددها وارد مدل می‌شن و پردازش (که تو [[chat bot theory]] بخش «مدل زبانی بزرگ چجوری کار می‌کنه» توضیح داده شد) روشون انجام می‌شه، و در آخر همین مسیر برعکس طی می‌شه (شناسه → توکن → متن) تا جواب قابل‌خوندن بشه.

### ارتباط با پروژه

هر بار که با `tiktoken` یا مشابهش طول یه پیام رو می‌شماری، داری دقیقاً مرحله ۲ و ۳ رو خودت جلوتر از سرور اجرا می‌کنی.

---

## ۲. TTFT — Time To First Token

### تشبیه ساده

> سفارش غذا می‌دی. TTFT یعنی از لحظه سفارش تا وقتی اولین لقمه جلوت گذاشته می‌شه — نه کل غذا، فقط لقمه اول.

### تعریف

مدت‌زمانی که از لحظه فرستادن درخواست تا رسیدن **اولین** توکن جواب طول می‌کشه.

### چرا مهمه

حتی اگه کل جواب کند تولید بشه، اگه TTFT کم باشه، کاربر حس می‌کنه بات «فوری جواب داد» — چون بلافاصله چیزی رو صفحه ظاهر می‌شه (این حس فقط وقتی وجود داره که جواب به‌صورت جریانی/streaming نمایش داده بشه).

### ارتباط با پروژه

از وقتی `stream=True` رو تو `bot()` اضافه کردیم (توضیح کامل تو بخش ۸)، دیگه TTFT با کل Latency برابر نیست — اولین `delta` که از حلقه‌ی چانک‌ها می‌رسه، همون لحظه‌ی TTFT حساب می‌شه. فقط هنوز واقعاً با `time.time()` اندازه‌گیریش نکردیم، صرفاً از نظر مفهومی جدا شده.

---

## ۳. TPOT — Time Per Output Token

### تشبیه ساده

> بعد از لقمه اول، هر لقمه بعدی چقدر طول می‌کشه بیاد؟ این میانگین فاصله بین لقمه‌هاست.

### تعریف

میانگین زمانی که طول می‌کشه هر توکن **بعد از توکن اول** تولید بشه. هرچه TPOT کمتر باشه، جریان جواب روون‌تر و طبیعی‌تر به نظر می‌رسه.

### ارتباط با پروژه

الان اندازه‌گیری نمی‌شه؛ برای اندازه‌گیریش باید زمان بین تولید هر توکن رو موقع streaming ثبت کرد.

---

## ۴. Latency (تاخیر کلی)

### تعریف

کل زمانی که از لحظه فرستادن درخواست تا دریافت **کامل** جواب طول می‌کشه.

### رابطه با دوتای بالا

```
Latency ≈ TTFT + (TPOT × تعداد توکن‌های خروجی)
```

### ارتباط با پروژه

گزارش فعلی (`report()`) فقط تعداد توکن و هزینه رو حساب می‌کنه، زمان رو نه. برای اضافه‌کردنش کافیه قبل و بعد فراخوانی `llm.chat.completions.create` با `time.time()` زمان بگیری و تفاضلشون رو حساب کنی.

---

## ۵. شمارش توکن قبل از درخواست

### تعریف

قبل از اینکه پیام رو واقعاً به سرور بفرستی، با یه کتابخونه محلی (مثل `tiktoken`) حدس می‌زنی پیام چند توکنه — بدون اتصال به اینترنت.

### چرا لازمه

- جلوگیری از رد شدن از سقف context window مدل
- تخمین هزینه **قبل از خرج‌کردن**
- محدودکردن طول ورودی کاربر (دقیقاً کاری که تو `chat_bot.py` با رد پیام‌های بالای ۱۰ توکن انجام دادی)

### ✅ نکته‌ای که قبلاً مشکل بود، الان حل شده

نسخه اول این پروژه از `tiktoken` با انکودینگ `cl100k_base` استفاده می‌کرد که توکنایزر رسمی مدل‌های OpenAI بود، نه توکنایزر واقعی مدل `poolside/laguna-s-2.1` — یعنی شمارش فقط تخمین بود. تو نسخه فعلی این با

```python
from transformers import AutoTokenizer
encoding = AutoTokenizer.from_pretrained('poolside/Laguna-S-2.1')
```

حل شده: `AutoTokenizer` دقیقاً توکنایزر خودِ همون مدل رو از HuggingFace دانلود و لود می‌کنه، پس الان شمارش قبل از درخواست **دقیقه**، نه تخمینی.

### ارتباط با پروژه

خط `encoding.encode(user_input)` تو `chat()` دقیقاً همین کاره — فقط حالا `encoding` از منبع درستی میاد.

---

## ۶. شمارش توکن بعد از درخواست

### تعریف

بعد از برگشتن جواب از سرور، خودِ سرویس تو فیلد `usage` می‌گه دقیقاً چند توکن ورودی و چند توکن خروجی مصرف شده — این عدد همیشه **دقیق‌تر** از تخمین قبل از درخواسته، چون خود مدل حسابش کرده.

### ارتباط با پروژه

`response.usage.total_tokens`, `.prompt_tokens`, `.completion_tokens` دقیقاً همین‌ان.

---

## ۷. محاسبه هزینه

### فرمول کلی

```
هزینه = (تعداد توکن ورودی × قیمت هر توکن ورودی) + (تعداد توکن خروجی × قیمت هر توکن خروجی)
```

نکته: قیمت‌ها معمولاً به ازای هر **یک میلیون توکن** اعلام می‌شن، پس باید تقسیم بر `1,000,000` بشه.

### ارتباط با پروژه

خط آخر `report()`:

```python
(self.input_token * 0.05 + self.output_token * 0.08) / 1_000_000
```

دقیقاً همین فرمول با اعداد قیمت واقعی مدل جایگزین شده.

## ۸. استریم کردن جواب (Streaming)

### تشبیه ساده

> فرق بین اینکه یه نویسنده کل کتاب رو بنویسه و یه‌جا بهت بده، با اینکه هر جمله رو تموم می‌کنه و همون لحظه ورقش رو جلوت می‌ذاره. جواب یکجا یعنی حالت اول؛ استریم یعنی حالت دوم.

### تعریف

به‌جای اینکه منتظر بمونی مدل **کل** جواب رو تولید کنه و بعد یک‌جا بهت بده، سرور جواب رو به‌صورت تکه‌های کوچیک (chunk) همون لحظه که تولید می‌شن می‌فرسته — دقیقاً همون چیزی که تو چت‌بات‌های معروف می‌بینی که جواب کلمه‌به‌کلمه ظاهر می‌شه.

### چطور تو کد کار می‌کنه

```python
response = self.llm.chat.completions.create(
    ...,
    stream=True
)

for chunk in response:
    if chunk.choices:
        delta = chunk.choices[0].delta.content
        if delta:
            print(delta, end="", flush=True)
```

- `stream=True` به سرور می‌گه جواب رو تکه‌تکه بفرست، نه یک‌جا.
- به‌جای یه جواب کامل، الان یه **حلقه از چانک‌ها** برمی‌گرده؛ هر چانک ممکنه یه تکه کوچیک از متن جواب (`delta.content`) داشته باشه یا هیچی.
- هر بار که یه تکه جدید می‌رسه، فوری چاپ می‌شه (نه اینکه صبر کنیم همه‌چیز جمع بشه)، پس کاربر جواب رو زنده می‌بینه.

### نکته مهم درباره `usage` تو حالت استریم

تو حالت عادی (بدون استریم)، عدد مصرف توکن همراه با کل جواب یه‌جا می‌رسید. تو حالت استریم، سرور این عدد رو فقط تو **آخرین چانک** می‌فرسته (بعد از تموم‌شدن تولید متن) — برای همین تو کد باید هر چانک رو چک کنی که `chunk.usage` داره یا نه، و فقط وقتی داشت جمعش بزنی.

### `flush=True` تو `print` دقیقاً چیه؟

وقتی پایتون یه `print` رو اجرا می‌کنه، معمولاً متن رو فوری روی صفحه نشون نمی‌ده — اول تو یه حافظه‌ی موقت (بافر) جمع می‌کنه و فقط وقتی این بافر پر بشه یا خط عوض بشه (`\n` بیاد)، همه‌ی محتوای جمع‌شده رو یک‌جا روی صفحه خالی می‌کنه. این کار برای بهینه‌سازی سرعته (نوشتن پشت‌سرهم روی صفحه گرون‌تره تا جمع‌کردن و یه‌جا نوشتن).

**مشکل اینجا:** تو استریم، هر بار فقط یه کلمه یا نصفه‌کلمه (`delta`) داری، نه یه خط کامل با `\n`. اگه `flush=True` رو ندی، پایتون این تکه‌ها رو تو بافر نگه می‌داره و ممکنه چند تکه با هم، با تاخیر، یا حتی همه در آخر یک‌جا چاپ بشن — یعنی دقیقاً همون جلوه‌ی کلمه‌به‌کلمه رو از بین می‌بره. `flush=True` می‌گه: «بافر رو دور بنداز، همین الان هرچی هست رو مستقیم روی صفحه بنویس.»

**تشبیه:** مثل اینکه به‌جای اینکه صبر کنی سطل آب پر بشه و یه‌جا خالیش کنی، هر بار که یه قطره اضافه می‌شه، همون لحظه می‌ریزیش بیرون.

### ارتباط با پروژه

بدون `flush=True`، حتی با `stream=True` هم ممکن بود جواب هنوز یک‌جا (یا با تاخیر عجیب) روی صفحه ظاهر بشه — این خط دقیقاً همون چیزیه که جلوه‌ی «زنده تایپ‌شدن» رو واقعی می‌کنه.

## 🎯 جمع‌بندی زنجیره کامل

```
متن → توکنایزر → توکن → شناسه توکن → پردازش مدل → شناسه توکن خروجی → توکن → متن جواب
```

همزمان با این مسیر، سه معیار زمانی (TTFT، TPOT، Latency) سرعت رو می‌سنجن، دو نوع شمارش توکن (قبل و بعد از درخواست) هزینه و محدودیت رو کنترل می‌کنن، و استریم کردن باعث می‌شه به‌جای منتظرموندن برای کل جواب، همون توکن‌ها رو یکی‌یکی و زنده ببینیم.
